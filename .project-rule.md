# ZeroPlatform Directives

## 1. Architecture & Dependency Invariants
- **Tier 0A (Absolute Bedrock)**: `ZeroPrimitives.Core` has `0` internal `Zero*` dependencies and `0` external NuGet dependencies on `net8.0`.
- **Tier 0B (Core Substrate)**: `ZeroConcurrency`, `ZeroSecurity`, and `ZeroText` depend only on Tier 0A (`ZeroPrimitives.Core`).
- **Tiers 1–5**: Downstream-only DAG ($L_N \rightarrow L_{<N}$); zero circular dependencies across `ZeroPlatform.slnx`.
- **Pragmatic Dual-Tier Allocation**: Zero heap allocations on hot paths (`Span<T>`, `ref struct`, `ArrayPool<T>`, SIMD intrinsics); idiomatic minimal-allocation OOP on cold paths.

## 2. Versioning & Release Governance (SSOT)

`ZeroPrimitives` is versioned and released **independently** from `ZeroPlatform` inside this monorepo.
> Apply the bump rules below only when §5 Release Gate is opened by an explicit user release request.

| Change Scope | File to Edit | Bump Rule | Git Tag & Workflow | Forbidden Action (Guardrail) | Verification Criterion |

### MSBuild CLI Override Rules
- Override `ZeroPlatform` version via `-p:PlatformVersion=X.Y.Z` (safe; leaves `ZeroPrimitives` untouched).
- Override `ZeroPrimitives` version via `-p:PrimitivesVersion=X.Y.Z` (safe; leaves `ZeroPlatform` untouched).
- Prerelease suffixes use `-p:VersionSuffix=<suffix>` (e.g. `primitives-v3.2.0-preview.1`); `FileVersion` remains numeric `$(VersionPrefix).0`.

## 3. Multi-Targeting & Verification Discipline
- Run `ZeroPrimitives.Tests` without `-f net8.0` so both `net8.0` and `net462` execute on every change.
- Do not force higher-tier modules to target `net462`/`netstandard2.0` unless consumer/API requirements demand it (`ZeroPrimitives.Core` and Tier 0B retain `netstandard2.0;net462;net8.0`).
- Stage only in-scope files (`git add <files>`); never commit tracked `.nupkg` artifacts.

## 4. Commit Message Convention
- **Format**: `[YYYY-MM-DD HH:mm] <type>(<scope>): <subject>`
- **Timestamp**: Local time (UTC+07:00) at commit time; generate with `Get-Date -Format "yyyy-MM-dd HH:mm"` immediately before `git commit` — never hand-type it.
- **Type**: `feat | fix | perf | refactor | docs | test | build | ci | chore | release`.
- **Scope**: Lowercase subsystem name without the `Zero` prefix (e.g., `primitives`, `ui`, `concurrency`), or `platform` for root/cross-cutting changes.
- **Subject & Body**: Imperative Standard Technical English with no trailing period and no subjective praise; optional body after a blank line; release commits reference the tag (e.g., `Release: primitives-v3.1.2`).
- **Example**: `[2026-11-27 09:15] fix(primitives): reject VarInt 5th-byte overflow payloads`
- **Guardrails**: Keep commits atomic (1 fix/feature = 1 commit), stage only in-scope files (`git add <files>`), and never rewrite already-pushed history.

## 5. Release Gate (Explicit User Request Only)
- **Default (upgrade/fix work)**: Leave `VersionPrefix` / `PlatformVersion` / `AssemblyVersion` unchanged; create no git tags, no GitHub Releases, and no manual `workflow_dispatch` publishes. Commit and push to `master` normally (CI-only workflows run; publishing triggers only on tags).
- **Change Log**: Record every user-visible change under `## Unreleased` at the top of the affected subsystem `CHANGELOG.md`.
- **Release Trigger**: Only when the user explicitly requests a NuGet release:
  1. Pick the SemVer bump from `## Unreleased` (patch = fixes only, minor = additive APIs, major = breaking changes).
  2. Edit `VersionPrefix` (and `AssemblyVersion` only for majors) per §2.
  3. Rename `## Unreleased` to `## <version> — <YYYY-MM-DD>`.
  4. Commit `[YYYY-MM-DD HH:mm] release(<scope>): <version>` and push `master`.
  5. Create and push the tag (`primitives-v<version>` or `v<version>`), then monitor `.github/workflows/publish-packages.yml` until it succeeds.
- **Guardrail**: Never create or push a release tag in the same turn as upgrade work unless the user asked to release.
